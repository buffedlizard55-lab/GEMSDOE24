## 3. Verified geometry of the 0.2778 file (B2) versus its family

Computed by [`scripts/verify_focus_family.py`](../scripts/verify_focus_family.py) from the raster bytes:

| Test | Result |
|---|---|
| Grid (all 11 files) | EPSG:32611, shape (3730, 3292), transform 100 m, float32 |
| B2 dot count (value == 1, finite) | 37,654 |
| D2.8 `gemsdoe30-d28-poisson300m-offcat-44090` dot count | 44,090 |
| B2 ∩ D2.8 | 37,654 (**all** B2 dots are D2.8 dots) |
| D2.8 dots not in B2 | **6,436** |
| Distance to public catalogue (`data/bridge/existing_faults.tif`) of the 6,436 removed dots | min 1.00 px, median 1.00, p90 2.00, max 2.00 |
| Distance to catalogue of B2's kept dots | min 2.24 px, median 19.65 px, p90 68.01 px |
| Directed 3-px overlap B2 → D2.8 | 100.00% |
| Directed 3-px overlap D2.8 → B2 | 88.17% |

**What is observed (pixel geometry, verified):** B2 is D2.8 with the dots that sit 1–2 px from the public fault catalogue removed, and the 37,654-dot budget is then met. Nothing else changed.

**Why it plausibly scores higher (hypothesis, not measured):**
- The official formula (DrivenData problem page) scores false positives as `FP_w = Σ p(x)·[1 − max_g k(d(x,g))]` with `α = 0.2`. A dot 1–2 px from a catalogue trace is close to a *known* fault, so it is only partly credited if a *new* truth fault is nearby; its FP penalty is therefore not zero.
- The official text also says the existing fault data "may be misaligned" from the true surface fault, so a 1–2 px halo around the catalogue is exactly where a misregistration artefact would sit. Dots there are the most likely to be wrong for reasons that are not geology.
- The repo's reimplementation of the metric (`src/gems/metric.py`, which cites the official page) excludes catalogue pixels from scoring (`active = valid & ~known`). The official page text read here does **not** state this exclusion explicitly, so it is flagged as an assumption. If it holds, dots *on* the catalogue are neutral and dots 1–2 px *off* it are not. Removing exactly that band is the minimal change that removes near-catalogue false positives while keeping the rest of D2.8.
- **Named non-fault mimic:** catalogue misregistration / rasterisation halo (the official text names both rasterisation off-by-one and label misalignment). B2's gain could be from removing a registration halo, not from better fault detection.
- **Unobservable:** whether the removed dots covered hidden truth. The hidden new-fault labels are not in this environment, so the sign and size of the true effect cannot be measured here. The owner's 0.2600 → 0.2778 gain is unverified.

**Why this does not give a path to a higher score:** the only mechanism-level lever this analysis found (remove the catalogue halo) is already applied in B2. A variant that also removes 3-px-halo dots would overlap B2 by well over 95% and is therefore a duplicate under the repo's rule. Going further needs new geology, and §6 explains why the local holdout cannot validate it.

## 5. Why the portal said "Predicted values must be in range [0, 1]"

Facts (verified here):
1. The official format text says the file must be single-layer `float32`, values in `[0, 1]`, same CRS/shape/bounds, and "**data outside the bounds is null or nan**" ([problem page, Submission format](https://www.drivendata.org/competitions/306/competition-doe-gems/page/967/)).
2. The reference solution initialises its output with `np.zeros` and writes the full array with no nodata value ([reference notebook, cells 16 and 19](https://github.com/drivendataorg/gems-prize-reference-solution/blob/aebe92f7c8a990f0e3443451b7a825d9afd6336b/unet-mc-cv-reference-solution.ipynb); commit `aebe92f`).
3. The repo's `-nan` files have NaN in exactly the 7,111,787 cells outside the 5,167,373-cell footprint (12,279,160 − 5,167,373 = 7,111,787), and finite values in [0, 1] inside it. This matches the official wording.
4. The repo's `-zeros` files are finite everywhere, in [0, 1], with 0 outside the footprint. This is within range but does not use the official NaN option.

Inference (not confirmed): a portal range check written as `(v >= 0) & (v <= 1)` returns False for NaN, so NaN cells can produce exactly this message. The all-finite `-zeros` file avoids that check. **We do not know which file was uploaded, and we do not know the portal's check.** The exact file name and SHA-256 that were uploaded would settle this; that is requested in §8.

## 7. Hypotheses (ranked; none implemented or validated in this session)

Ranked by expected value per unit cost, with an honest status. The first is the one that could change the leaderboard; it is blocked by data we cannot access.

1. **Replace the catalogue-proxy holdout with a truth-independent check (cost: low, value: high).** Before any further holdout claim, rebuild the truth from a source that is *not* the catalogue. Candidate official sources: the USGS Quaternary Fault and Fold Database (catalogue, not useful alone) and the INGENIOUS labels referenced by the problem page. Status: the official label files are behind the DrivenData login (the repo's `scripts/download_competition_data.sh` cannot authenticate), and INGENIOUS access was not checked here. **Not verified as obtainable from this sandbox.**
2. **Residualised DEM gradients to remove highway cut-and-fill (cost: medium, value: medium).** Repo lane `H24-S3DEP1` flagged 10 m highway cut/fill (C2ST AUC 0.6012). Needs ScienceBase 3DEP tiles. ScienceBase item page is reachable via the page fetch tool ([USGS ScienceBase 3DEP item](https://www.sciencebase.gov/catalog/item/4f70aa9fe4b058caae3f8de5)), but the bulk tiles are not in this sandbox's egress allow-list (`github.com`, `codeload.github.com`, `api.github.com`, `registry.npmjs.org`, `pypi.org`, `files.pythonhosted.org`). **Viable only if the tiles are fetched by an allowed route.**
3. **Catalogue-halo-aware dotting (cost: low, value: unknown).** Explicitly model the 1–2 px misregistration band around the catalogue as a *negative* prior, instead of a hard removal. This is the mechanism behind B2. **Uniqueness problem:** it converges on B2 (>95% overlap). Not submittable as a new file.
4. **External orthogonal grids (Sentinel-2 SWIR alteration, USArray MT, InSAR velocity steps).** Named in the repo's next-step list. Not obtainable here without the blocked hosts; not validated.

None of these is ready to spend a weekly slot. The protocol in `AGENTS.md` allows at most three experiments per session; this session used **zero** experiments and generated **no** new raster.
